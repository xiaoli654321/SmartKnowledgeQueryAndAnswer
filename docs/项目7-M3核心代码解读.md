## 0. 一次问答的完整路径

```
用户 POST /ai/ask {"question":"入职满一年能休几天年假","tenantId":1001}
   │
   ▼ AiController.ask
   ▼ RagService.ask
   ├─ 1. SearchClient.hybrid(...)          Feign → search-service，拿 top5 片段
   │      └─ 空结果 → 直接返回"无法回答"，不调模型
   ├─ 2. PromptBuilder.build(question, hits)   片段编号 + 三条规则
   ├─ 3. GovernedChatService.chat(prompt)
   │      ├─ @RateLimiter  20 次/10s
   │      ├─ @CircuitBreaker  失败率 >50% 打开
   │      ├─ @Retry  最多 3 次
   │      └─ FailoverChatService → [GLM-5.3-Flash, ollama:qwen3:1.7b] 逐个试
   ├─ 4. TokenMeterService.record(tenant, provider, in, out)   → Redis
   ├─ 5. 组装 citations（回答里的 [n] ↔ 这里第 n 条）
   └─ 6. MetricReporter.reportAsync(...)   @Async，不阻塞用户
```

## 1. 契约：`LlmReply` 与 `LlmProvider`

```java
public record LlmReply(String content, long inputTokens, long outputTokens, String provider) { }

public interface LlmProvider {
    String name();
    LlmReply chat(String prompt) throws Exception;
}
```

**为什么 `LlmReply` 必须带 token**：计量只能用供应商返回的真实 usage。

自己在 Java 里按字数估算是错的：中英文、标点、特殊符号的计费口径不同，估算值会系统性偏低或偏高 —— 而"计量不准"直接让成本核算和配额控制失真。

**为什么抽象成接口**：每家协议不同（OpenAI 兼容 vs Ollama 原生），字段名、用量字段全不一样。抽象之后，Failover 只认 `chat(prompt) → LlmReply`，加一家供应商就是新增一个 `@Component`。

## 2. OpenAiProvider：协议字段是唯一的坑

请求体就三样东西：

```java
Map<String,Object> body = Map.of(
    "model", model,
    "messages", List.of(
        Map.of("role","system","content","你是企业知识库问答助手，只依据给定资料回答。"),
        Map.of("role","user","content", prompt)),
    "temperature", 0.2,
    "stream", false);
```

解析要注意两个名字：

```java
JsonNode choice = node.path("choices").path(0);        // ★ choices（复数）
long in  = node.path("usage").path("prompt_tokens").asLong(0);
long out = node.path("usage").path("completion_tokens").asLong(0);
```

### 实际踩过的 bug（值得单独记）

第一版写成了 `node.path("choice")` —— 少一个 s。`path()` 找不到时返回 `MissingNode` 而不是抛异常，于是 `isMissingNode()` 恒为 true，**每次调用都进异常分支**，把明明成功的响应当成"结构异常"扔掉。

异常消息里其实带着完整响应，里面清清楚楚写着 `"choices":[...]`：

```
IllegalStateException: 供应商返回结构异常：
{"id":"01a202d2...","object":"chat.completion","choices":[{"index":0,"message":{...}}]}
```

> 教训：解析外部 JSON 时，**异常里一定要带上原始响应**（这段代码已经这么做了）。
> 排障成本取决于"证据有没有留在现场"，而不是取决于你猜得准不准。

两个必须处理的边界：

| 边界 | 处理 | 不处理的后果 |
|---|---|---|
| `choices` 缺失 | 抛 `IllegalStateException` + 原始响应前 200 字 | 后面 NPE，现场丢失 |
| `content` 为空 | 抛异常 | 空字符串被当成"答案"返回给用户 |

## 3. OllamaProvider：字段名完全不一样

```java
Map<String,Object> body = Map.of(
    "model", model,
    "messages", List.of(Map.of("role","user","content", prompt)),
    "stream", false);

String content = node.path("message").path("content").asText("");
long in = node.path("prompt_eval_count").asLong(0);   // 不是 prompt_tokens
long out = node.path("eval_count").asLong(0);          // 不是 completion_tokens
```

`name()` 返回 `"ollama:" + model`，这样日志和指标里能一眼看出来"这次降级到了本地"。

存在的意义：云厂商挂了、欠费、断网时，至少还能给一个质量差但可用的答案 —— **降级，而不是归零**。

## 4. FailoverChatService：顺序 + 计时

```java
this.providers = providers.stream()
        .sorted(Comparator.comparing(p -> p.name().contains("ollama")))   // 非 ollama 在前
        .toList();
```

构造时打一行日志，确认顺序：

```
LLM 供应商顺序：[zai-org/GLM-5.3-Flash, ollama:qwen3:1.7b]
```

主循环：

```java
for (LlmProvider p : providers) {
    Timer.Sample sample = Timer.start(meterRegistry);
    try {
        LlmReply reply = p.chat(prompt);
        sample.stop(Timer.builder("llm.call.duration")
                .tag("provider", p.name()).tag("result", "success").register(meterRegistry));
        meterRegistry.counter("llm.call.total", "provider", p.name(), "result", "success").increment();
        return reply;
    } catch (Exception e) {
        sample.stop(...tag("result","fail")...);
        meterRegistry.counter("llm.call.total", ... "fail").increment();
        log.warn("供应商 {} 失败，切换下一家：{}", p.name(), e.getMessage());
    }
}
throw new ResponseStatusException(SERVICE_UNAVAILABLE, "所有 LLM 供应商均不可用…");
```

三个设计点：

| 点 | 为什么 |
|---|---|
| **按 provider 打标签** | 只有"总耗时"时，你分不清是"云端变慢"还是"降级到本地了"——处置方式完全不同 |
| **warn 日志带供应商名** | 排障第一眼就能确认是不是供应商侧问题 |
| **全失败才 503** | 有一家成功就正常返回，用户完全无感 |

### 排序的坑

```java
// 错：Boolean.compare(b.contains, a.contains) → 顺序反转，每次都先打本地小模型
// 对：按 contains("ollama") 升序 → false(云端) 在前
.sorted(Comparator.comparing(p -> p.name().contains("ollama")))
```

写反了不报错，只是慢（17s vs 6.6s）且答案质量差，日志里还显示"成功"——**最难发现的那类 bug**。

## 5. GovernedChatService：注解顺序就是语义

```java
@RateLimiter(name = "llmRateLimiter", fallbackMethod = "rateLimited")   // 最外：先挡超量
@CircuitBreaker(name = "llmBreaker", fallbackMethod = "circuitOpen")    // 中间：快速失败
@Retry(name = "llmRetry", fallbackMethod = "retryExhausted")            // 最内：只重试可重试的
public LlmReply chat(String prompt) {
    return failoverChatService.chat(prompt);
}
```

三个 `name` 必须和 yml 的 `resilience4j.*.instances` 一字不差。旧工程写成注解 `llmRateLimiter`、配置 `ratelimiter`，限流静默失效且不报错。

三个 fallback 的语义必须分清：

| 触发 | 返回 | 语义 |
|---|---|---|
| 令牌桶满 | **429** | "等会儿再来"，不是故障 |
| 熔断打开 | **503** | 暂时不可用，快速失败 |
| 重试耗尽 | **503** | 透传真实原因 |

```java
private LlmReply retryExhausted(String prompt, Throwable e) {
    if (e instanceof ResponseStatusException rse) {
        throw rse;                       // 已经是明确状态码（429/503），原样抛
    }
    throw new ResponseStatusException(SERVICE_UNAVAILABLE, "LLM 调用失败：" + e.getMessage());
}
```

### 熔断器把"被限流"当失败 —— 实测踩到的坑

第一次并发测试结果是**25 个请求全部 503**，而不是 20 个 200 + 5 个 429。

原因：限流拒绝抛出的 `RequestNotPermitted` 被熔断器计为失败，失败率一过阈值熔断打开，后面全变成"服务不可用"。

修复在 yml：

```yaml
resilience4j:
  circuitbreaker:
    instances:
      llmBreaker:
        ignore-exceptions:
          - io.github.resilience4j.ratelimiter.RequestNotPermitted
```

修完实测 `20×200 + 5×429`，语义正确。

## 6. SearchClient：Feign + 镜像 DTO

```java
@FeignClient(name = "search-service")
public interface SearchClient {
    @PostMapping("/search/hybrid")
    List<SearchHitDto> hybrid(@RequestBody SearchQuery query);
}
```

`name` 必须等于 search-service 的 `spring.application.name`，配合 loadbalancer 走 `lb://`。

`SearchHitDto` 是 search-service 里 `SearchHit` 的**镜像**——跨服务不共享类，字段名对不上会得到一堆 null 且不报错。这和 M2 的事件契约是同一类问题。

## 7. PromptBuilder：三条规则缺一不可

```java
sb.append("【参考资料】\n");
for (int i = 0; i < hits.size(); i++) {
    sb.append("[").append(i + 1).append("] （文档ID ").append(h.documentId())
      .append("，片段 ").append(h.chunkIndex()).append("）\n")
      .append(h.content()).append("\n\n");
}
sb.append("【用户问题】\n").append(question).append("\n\n");
sb.append("【回答要求】\n")
  .append("1. 只使用上方参考资料中的信息，不要编造，不要引入资料以外的常识；\n")
  .append("2. 答案中的每个关键结论后面用 [编号] 标注依据；\n")
  .append("3. 如果参考资料不足以回答，直接回答“根据现有知识库无法回答该问题”，不要猜测；\n")
  .append("4. 用简洁的中文回答，不要复述参考资料原文。\n");
```

| 规则 | 缺了会怎样 |
|---|---|
| 只用资料 | 模型拿训练记忆里的"通用常识"答企业制度，答得很像但不对 |
| 标 `[n]` | 不可溯源，RAG 退化成普通聊天，用户无法核对 |
| 资料不足就明说 | 找不到也要编一段，比"不知道"危险得多 |

编号是**有意的**：`[i+1]` 与返回的 `citations` 里 `index=i+1` 一一对应，前端点 `[2]` 就能跳到第二段原文。

## 8. RagService：两处刻意设计

```java
List<SearchHitDto> hits = searchClient.hybrid(new SearchQuery(question, tenantId, topK));
if (hits == null) hits = List.of();

if (hits.isEmpty()) {
    return new AskResponse("根据现有知识库无法回答该问题（未检索到相关内容）。",
            List.of(), "none", 0, 0, System.currentTimeMillis() - start);
}
```

**设计 1：空检索短路。** 检索为空还去调模型，只会得到一段编造的话，既费钱又误导。这一行同时实现了"省 token"和"防幻觉"。

**设计 2：旁路不拖垮主流程。**

```java
tokenMeterService.record(tenantId, reply.provider(), reply.inputTokens(), reply.outputTokens());
...
metricReporter.reportAsync(question, hits, reply.content());
```

计量内部 catch 掉所有异常只记日志；评测是 `@Async`。两者都失败，用户照样拿到答案。

出处组装：

```java
String snippet = h.content().substring(0, Math.min(160, h.content().length()));
citations.add(new Citation(i + 1, h.documentId(), h.chunkIndex(), snippet, h.score()));
```

截 160 字是为了响应体不臃肿，前端够用。

## 9. TokenMeterService：为什么必须是 Redis

```java
redis.opsForValue().increment("token:tenant:" + tenantId, total);
redis.opsForValue().increment("token:provider:" + provider, total);
```

ai-service 是无状态的、会横向扩多个实例。用进程内 `Map` 的话，"本月用了多少 token"取决于负载均衡把请求打到哪台 —— 这个数字没有意义。

两个 key 的分工：

| key | 用途 |
|---|---|
| `token:tenant:{id}` | 计费、配额、按租户限流 |
| `token:provider:{name}` | 成本分析：哪家花得多，要不要切换 |

生产上还应加时间维度（`token:tenant:{id}:2026-11`），否则没法做月度账单。

## 10. MetricReporter：@Async 的两个前提

```java
@Async
public void reportAsync(String question, List<SearchHitDto> hits, String answer) {
    if (!enabled) return;          // 服务没起时不刷错误日志
    try { ... } catch (Exception e) { log.debug(...); }
}
```

- 启动类必须有 `@EnableAsync`；
- **调用方必须是别的 Bean**——同类内部自调用不走代理，`@Async` 会静默退化成同步，把几秒的评测时间加到用户头上。

## 12. 踩坑清单（M3 相关）

| 现象 | 根因 | 处理 |
|---|---|---|
| 每次调用都报"返回结构异常" | 解析 `choice`（少了 s），`path()` 返回 MissingNode 不抛异常 | 用 `choices`，并把原始响应带进异常 |
| 每次都先打本地小模型、又慢又差 | Failover 排序比较器写反 | `Comparator.comparing(p -> p.name().contains("ollama"))` |
| 突发流量下全变 503 | 熔断器把限流拒绝计为失败 | CB 配 `ignore-exceptions: RequestNotPermitted` |
| 429 被写成 503 | fallback 语义混用 | 限流 → 429，熔断 → 503，重试耗尽 → 透传 |
| Token 计量永远是 0 | 没取供应商的 `usage` | 解析 `usage.prompt_tokens/completion_tokens`（Ollama 是另外两个字段） |
| `@Async` 不生效 | 同类内部自调用 | 由别的 Bean 调用 + 启动类 `@EnableAsync` |
