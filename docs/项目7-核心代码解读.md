## 1. doc-service：把文件变成"可检索的块 + 一条事件"

### 1.1 解析层：接口 + 工厂，而不是 if-else

`parser/DocumentParser` 只有两个方法：`supports(filename)`、`parse(bytes)`。三个实现各管一种格式，`ParserFactory` 注入 `List<DocumentParser>` 后按扩展名挑一个：

```java
public String parse(String filename, byte[] bytes) throws IOException {
    DocumentParser parser = parsers.stream()
            .filter(p -> p.supports(filename))
            .findFirst()
            .orElseThrow(() -> new IllegalArgumentException(
                    "不支持的文件类型：" + filename + "，目前支持 .txt / .md / .pdf / .docx"));
    return parser.parse(bytes);
}
```

**为什么值得这么写**：将来加 PPT/Excel/OCR，只新增一个 `@Component`，工厂和 Service 一行都不用改。这是"对扩展开放、对修改关闭"最便宜的落地方式。

两个实现细节值得记：

| 实现 | 关键点 | 不这么写会怎样 |
|---|---|---|
| `TxtParser` | 先按 UTF-8 解，出现 `\uFFFD` 再按 GBK 解一次 | 中文 Windows 的老 txt 全是乱码，且不报错 |
| `PdfParser` | PDFBox **3.x** 的 `Loader.loadPDF(bytes)` | 抄 2.x 的 `PDDocument.load()` 直接编译不过 |
| `DocxParser` | 遍历 `getBodyElements()`，段落和 `XWPFTable` 都要取 | 只读段落 → 制度文档里的"天数表/标准表"整张丢失，用户问数字永远搜不到 |

### 1.2 切片层：500 字 + 100 字重叠，优先句末切

`chunk/TextChunker` 的算法四步：归一化 → 按句末标点切句 → 贪心装桶到 500 字 → 下一块带上一块末尾 100 字。

```java
for (String sentence : SENTENCE_END.split(text)) {
    for (String piece : hardSplit(sentence)) {
        if (current.length() > 0 && current.length() + piece.length() > MAX_CHARS) {
            String finished = current.toString().trim();
            chunks.add(finished);
            String overlap = tailOf(finished, OVERLAP_CHARS);   // ★ 从"已产出的块"取尾
            current.setLength(0);
            current.append(overlap);
        }
        current.append(piece);
    }
}
```

**这里踩过一个坑**：最开始 `overlap` 是从**未 trim 的缓冲区**取的，块末尾若有换行会被 trim 掉，导致下一块开头与上一块结尾错开 1 个字符 —— 重叠变成 99 字。改成"先 trim 成最终块，再从这一块取尾"，实测严格 100 字。

`hardSplit` 是兜底：一段 800 字、中间没有任何标点（比如一长串编号）时，必须按长度硬切，否则这一块永远超长、且循环可能不推进。

### 1.3 服务层：事务边界 + 提交后才发事件（本项目最核心的一段）

```java
@Transactional(rollbackFor = Exception.class)
public UploadResult upload(String title, Long tenantId, String filename, byte[] bytes) throws IOException {
    String text = parseAndValidate(filename, bytes);
    List<String> chunks = chunkAndValidate(text);

    KbDocument doc = new KbDocument();
    doc.setTenantId(tenantId);
    doc.setTitle(title);
    doc.setContent(text);
    docMapper.insert(doc);              // MP 把自增 id 回填到 doc.id

    int version = 1;
    insertVersion(doc.getId(), version, text);

    DocumentIndexedEvent event = buildEvent(doc, version, chunks);
    afterCommit(() -> publisher.publish(event));   // ★ 不是直接 publish
    return new UploadResult(doc.getId(), version, chunks.size(), text.length());
}
```

**为什么不直接发**：先发消息、后提交事务，一旦事务回滚，检索侧已经建好索引、库里却没有这篇文档 —— 数据和索引长期不一致。正确做法是注册事务同步回调：

```java
private void afterCommit(Runnable action) {
    if (TransactionSynchronizationManager.isSynchronizationActive()) {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override public void afterCommit() { action.run(); }
        });
    } else {
        action.run();   // 没有事务（单测/直调）就地执行
    }
}
```

日志能验证：业务方法早已返回，事件发送发生在 Kafka 的 `producer-1` 线程上。

其余三个方法共用一条规则：**所有读写都带 `tenant_id`**。

```java
private KbDocument requireDoc(Long docId, Long tenantId) {
    KbDocument doc = docMapper.selectOne(new QueryWrapper<KbDocument>()
            .eq("id", docId)
            .eq("tenant_id", tenantId));
    if (doc == null) throw new ResponseStatusException(HttpStatus.NOT_FOUND, "文档不存在：" + docId);
    return doc;
}
```

- 查不到统一 404，不区分"不存在"与"不是你的"，避免被人枚举文档 ID；
- `versions()` 先 `requireDoc` 再列版本，否则可以越租户列别人的版本历史。

**版本链**：`addVersion` 用 `selectMaxVersion + 1`；`rollback` 不是"删掉新版本"，而是**把老内容写回主表 + 追加一条新版本**，历史永远可追溯。空表时 `MAX()` 返回 NULL，所以 SQL 里必须 `IFNULL(MAX(version),0)`。

### 1.4 Kafka 生产者：异步发送必须接回调

```java
CompletableFuture<SendResult<String, Object>> future =
        kafkaTemplate.send(TOPIC, String.valueOf(event.docId()), event);
future.whenComplete((result, ex) -> {
    if (ex != null) { log.error("事件发送失败 docId={}", event.docId(), ex); return; }
    log.info("事件发送成功 partition={} offset={}", result.getRecordMetadata().partition(),
             result.getRecordMetadata().offset());
});
```

`send()` 是异步的。不接回调的后果：Kafka 挂了接口照样返回 200，但索引永远建不起来 —— 线上最难查的一类"静默丢消息"。

key 用 `docId`：同一文档的所有事件进同一分区，消费端天然按序，不会"版本 2 先到、版本 1 后到"把内容覆盖回旧版。

### 1.5 RBAC 切面：注解 + AOP，失败要"看得见"

`@RequirePermission("document:write")` 标在 Controller 方法上，`PermissionAspect` 用 `@Around("@annotation(requirePermission)")` 拦截，从 `X-User-Role` 取角色，越权抛 403。

要点是**注解的 `@Retention` 必须是 RUNTIME**，否则切面读不到；以及角色表先用内存 Map（生产要放配置中心，否则改权限得重新发版）。

## 2. search-service：消费事件建索引 + 两路召回

### 2.1 消费者：跨服务反序列化的三个配置

```java
@KafkaListener(topics = "doc-indexed", groupId = "search-index-group")
public void onMessage(DocumentIndexedEvent event) { ... }
```

生产者会把"自己的类全限定名"写进消息头，消费端没有那个类就会 `ClassNotFoundException`。所以 yml 里三件事缺一不可：

```yaml
spring.kafka.consumer.value-deserializer: org.springframework.kafka.support.serializer.JsonDeserializer
spring.kafka.consumer.properties.spring.json.use.type.headers: false                     # 忽略生产端的类名
spring.kafka.consumer.properties.spring.json.value.default.type: com.zjjxy.searchservice.event.DocumentIndexedEvent
```

事件类在两端各写一份（`record`，字段名必须一字不差），这是"跨服务不共享类"的代价，也是最容易埋雷的地方。

异常策略选的是"catch 住记日志、继续消费"，避免一条毒消息卡死分区；生产更稳的是进死信队列。

### 2.2 建索引：先删后插 = 幂等

```java
// 1) 幂等：清掉这篇文档的旧块（含旧版本）
chunkMapper.delete(new QueryWrapper<DocChunk>()
        .eq("document_id", event.docId())
        .eq("tenant_id", event.tenantId()));

// 2) 批量算向量（失败降级为 null）
List<float[]> vectors = tryEmbed(contents, docId);

// 3) 落库（有向量就写，没有就留空）
row.setEmbedding(vectors != null ? toJson(vectors.get(i)) : null);
```

**为什么要删**：文档改版会重发事件，不删就会出现新旧两份内容同时可检索，用户可能拿到已经作废的条款 —— 比"搜不到"危险得多。

**为什么允许降级**：embedding 服务抖动时，宁可"这篇只有关键词索引"，也不要整篇建不进去。日志里会明确写 `向量=无(降级)`。

### 2.3 Embedding 客户端：批量 + 按 index 归位

```java
float[][] ordered = new float[batch.size()][];
for (JsonNode item : resp.path("data")) {
    int idx = item.path("index").asInt(-1);
    ...
    ordered[idx] = arr;
}
```

服务端**不保证**返回顺序与入参一致。不按 `index` 归位，向量和文本就会错位 —— 检索结果"莫名其妙地不准"，而且完全不报错。

### 2.4 混合检索：两路 + RRF

```java
public List<SearchHit> hybrid(SearchRequest request) {
    List<KeywordHit> keywordHits = chunkMapper.keywordSearch(query, tenantId, keywordTopK);
    List<Scored> vectorHits = vectorSearch(query, tenantId);
    return fuse(keywordHits, vectorHits, limit);
}
```

关键词那一路靠 MySQL 全文索引（**`WITH PARSER ngram`**，默认分词器对中文基本无效）：

```sql
SELECT id, document_id, tenant_id, chunk_index, content,
       MATCH(content) AGAINST (#{q} IN NATURAL LANGUAGE MODE) AS score
FROM doc_chunk
WHERE tenant_id = #{tenantId}
  AND MATCH(content) AGAINST (#{q} IN NATURAL LANGUAGE MODE)
ORDER BY score DESC LIMIT #{limit}
```

向量那一路把候选捞进内存算余弦（`candidateLimit=2000` 保护内存），**向量服务失败时返回空列表**，让检索退化成"仅关键词"，而不是整个接口 500。

融合用 RRF 而不是加权求和：

```java
for (Merge m : list) {
    double s = 0;
    if (m.keywordRank != null) s += 1.0 / (rrfK + m.keywordRank);   // rrfK = 60
    if (m.vectorRank != null) s += 1.0 / (rrfK + m.vectorRank);
    m.score = s;
}
```

理由：MySQL 相关度可能是几十，余弦是 0~1，量纲完全不同，直接相加会让一路压死另一路。RRF 只看名次，与分值无关。

实测对照（同一份文档切成 2 块）：

| 查询 | 关键词 | 向量 | 结论 |
|---|---|---|---|
| `年假 五天` | 2 条 | 2 条 | 两路都命中，RRF 0.0328 |
| `跨城出差住宿最多报多少` | 1 条 | 2 条 | 差旅块两路第一；另一块**仅向量召回** |
| `我想请几天假出去玩` | **0 条** | 2 条 | 字面完全不重合，纯关键词直接零召回 —— 混合检索的价值所在 |

## 3. ai-service：RAG 编排 + 治理

### 3.1 供应商抽象：把"每家口径不同"关在实现里

`LlmProvider.chat(prompt)` 返回 `LlmReply(content, inputTokens, outputTokens, provider)`。

为什么一定要带回 token：计量必须用供应商返回的真实 usage。OpenAI 兼容协议叫 `usage.prompt_tokens/completion_tokens`，Ollama 叫 `prompt_eval_count/eval_count` —— 这种差异正是抽象成接口的价值。

### 3.2 Failover：排序 + 每个供应商单独计时

```java
this.providers = providers.stream()
        .sorted(Comparator.comparing(p -> p.name().contains("ollama")))   // 非 ollama 在前
        .toList();
```

**这里踩了个"不报错但很坑"的 bug**：最初写成 `Boolean.compare(b.contains, a.contains)`，顺序被反转，每次都先打本地小模型 —— 又慢（17s vs 6.6s）又差，日志里还显示"成功"。排序逻辑必须自己推一遍，别凭直觉。

计时指标按 provider 打标签：

```java
Timer.Sample sample = Timer.start(meterRegistry);
try {
    LlmReply reply = p.chat(prompt);
    sample.stop(Timer.builder("llm.call.duration")
            .tag("provider", p.name()).tag("result", "success").register(meterRegistry));
```

只有"总耗时"时，你分不清是云端变慢还是降级到了本地小模型 —— 这两件事的处置完全不同。

### 3.3 治理层：三个注解的顺序就是语义

```java
@RateLimiter(name = "llmRateLimiter", fallbackMethod = "rateLimited")   // 最外：先挡超量
@CircuitBreaker(name = "llmBreaker", fallbackMethod = "circuitOpen")    // 中间：快速失败
@Retry(name = "llmRetry", fallbackMethod = "retryExhausted")            // 最内：只重试可重试的
public LlmReply chat(String prompt) { return failoverChatService.chat(prompt); }
```

三个 `name` 必须和 yml 的 `resilience4j.*.instances` 一字不差 —— 旧工程就是注解写 `llmRateLimiter`、配置写 `ratelimiter`，限流静默失效。

fallback 的语义也要分清：限流 → 429（"等会儿再来"）；熔断 → 503（"暂时不可用"）；重试耗尽 → 透传真实错误。**把 429 写成 503 就是语义错位**，用户会以为服务挂了。

还有一个实测出来的坑：熔断器默认把"被限流"也计为失败。25 并发测试第一次结果是**全部 503**（限流拒绝 → 熔断计数 → 打开 → 后面全挂），加了 `ignore-exceptions: RequestNotPermitted` 才恢复成 `21×200 + 4×429`。

### 3.4 Prompt：三条规则缺一不可

```
1. 只使用参考资料中的信息，不要编造，不要引入资料以外的常识；
2. 每个关键结论后面用 [编号] 标注依据；
3. 资料不足时直接回答"根据现有知识库无法回答"，不要猜测。
```

缺第 1 条 → 模型拿训练记忆里的"通用常识"答企业制度；缺第 2 条 → 不可溯源，RAG 就退化成普通聊天；缺第 3 条 → 找不到也要编一段。

### 3.5 RagService：空检索直接短路

```java
List<SearchHitDto> hits = searchClient.hybrid(new SearchQuery(question, tenantId, topK));
if (hits.isEmpty()) {
    return new AskResponse("根据现有知识库无法回答该问题（未检索到相关内容）。",
            List.of(), "none", 0, 0, System.currentTimeMillis() - start);
}
```

检索为空还去调模型，只会得到一段编造的话，既费钱又误导。这是"省 token"和"防幻觉"同时成立的一处设计。

调用链：`searchClient.hybrid` → `governedChatService.chat` → `tokenMeterService.record` → 组装 `citations` → `metricReporter.reportAsync`。计量和评测都是**旁路**，任何异常都不能影响答案返回。

### 3.6 Token 计量：用 Redis 而不是 Map

```java
redis.opsForValue().increment("token:tenant:" + tenantId, total);
redis.opsForValue().increment("token:provider:" + provider, total);
```

ai-service 是无状态的、会横向扩多个实例。用进程内 `Map` 的话，"本月用了多少 token"取决于负载均衡把请求打到哪台 —— 数字没有意义。

### 3.7 MetricReporter：@Async 的两个前提

```java
@Async
public void reportAsync(String question, List<SearchHitDto> hits, String answer) {
    if (!enabled) return;          // 开关：M4 之前 metric-service 不存在，避免刷错误日志
    ...
}
```

- 启动类必须有 `@EnableAsync`；
- **调用方必须是别的 Bean** —— 同类内部自调用不走代理，`@Async` 会静默退化成同步。

## 4. gateway：WebFlux 上的 RBAC

```java
@Component
public class RbacGlobalFilter implements GlobalFilter, Ordered {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();
        if (path.startsWith("/actuator")) return chain.filter(exchange);   // ★ 监控必须放行

        boolean isRead = "GET".equals(method) || "HEAD".equals(method) || "OPTIONS".equals(method);
        if (isRead) return chain.filter(exchange);

        if (!WRITE_ROLES.contains(normalizedRole)) {
            exchange.getResponse().setStatusCode(HttpStatus.FORBIDDEN);
            exchange.getResponse().getHeaders().setContentType(MediaType.APPLICATION_JSON);
            byte[] body = ("{\"error\":\"无权限执行该操作（当前角色：" + normalizedRole + "）\"}")
                    .getBytes(StandardCharsets.UTF_8);
            return exchange.getResponse().writeWith(Mono.just(...wrap(body)));
        }
        return chain.filter(exchange);
    }
    @Override public int getOrder() { return -1; }
}
```

两个必须记住的点：

1. 网关是 **WebFlux**，不能用 Servlet 那套 `HttpServletResponse`，返回 403 要自己往 response 写 body；
2. **`/actuator/**` 必须放行**，否则 Prometheus 抓指标被 403 挡掉，现象是"Grafana 面板全空"，很容易查错方向。

方法级那层 `@RequirePermission` 仍然保留 —— 绕过网关直连 8082 时还能兜住，这是纵深防御，不是重复劳动。

## 5. metric-service：Python 侧的三个关键实现

### 5.1 ragas 0.4 的适配（版本差异是硬门槛）

```python
from ragas import RunConfig, evaluate
from ragas.metrics import answer_relevancy, context_precision, faithfulness
from ragas.llms import LangchainLLMWrapper

result = evaluate(
    ds, metrics=metrics, llm=_judge(), embeddings=_embeddings(), show_progress=False,
    run_config=RunConfig(timeout=300, max_workers=2),
)
```

- 0.4 的"现代化 API"要求 `llm_factory` + InstructorLLM，但 0.1 风格的 `evaluate(...)` 仍可用（讲义也是这套），所以走 legacy 路径；
- **`context_relevancy` 在 0.4 已被移除**，无参考答案时只能算 faithfulness / answer_relevancy；
- **`RunConfig` 必须显式给**：默认每任务 180s，faithfulness 最慢，多指标并发时必然超时并返回 `NaN`；`max_retries` 也要设 0，否则重试会把超时吃满。实测从"183s + NaN"降到"54s + 1.0"。

结果读取也不能用 `dict(result)`（0.4 的 `EvaluationResult` 会 `KeyError: 0`），要用 `result.scores`：

```python
per_sample = result.scores or []
for m in metrics:
    vals = [float(row[m.name]) for row in per_sample
            if isinstance(row.get(m.name), (int, float)) and not math.isnan(float(row[m.name]))]
    scores[m.name] = round(sum(vals) / len(vals), 4) if vals else None   # 没算出来就说 null，别假装 0 分
```

### 5.2 自动出题：LLM 输出必须容错解析

```python
text = re.sub(r"^```(?:json)?", "", text).strip()     # 剥 ```json
start, end = text.find("["), text.rfind("]")          # 截取数组
data = json.loads(text[start:end + 1])
```

模型经常在 JSON 外面裹一层代码块或加一句解释，直接 `json.loads` 十次有三次失败。

### 5.3 样本存储：JSONL 追加

评测是旁路服务（讲义明确"不建库、不进 Nacos"），所以 `samples.jsonl` 追加写最简单，出问题能直接打开看。`load(limit)` 只读最近 N 条 —— 评测不需要全量，越新越有代表性。

## 6. 横切约定（改代码前先看这一节）

| 约定 | 内容 | 违反的后果 |
|---|---|---|
| 端口 | gateway 8080 / ai 8081 / doc 8082 / search 8083 / metric 8090 | 和讲义不一致，网关路由对不上 |
| 服务名 | `spring.application.name` 必须等于 `lb://` 里的名字 | Feign 报 `No load balancer available` |
| 路径 | 服务 controller 自带 `/doc`、`/search`、`/ai` 前缀，网关**不剥前缀** | 加了 StripPrefix 就 404，两边必须一起改 |
| 租户 | 所有查询带 `tenant_id` | 越权读到别家数据 |
| 错误码 | 403 越权 / 404 不存在或不属本租户 / 400 参数或文件问题 / 429 限流 / 503 熔断或供应商全挂 | 语义错位，前端无法区分 |
| 指标 | `/actuator/prometheus` 暴露，`application` 标签由 yml 注入 | Grafana 无法按服务筛选 |

## 7. 六个"如果重来一次"的坑（浓缩版）

1. **事件在事务提交后发**（`afterCommit`），否则回滚后索引和库不一致；
2. **索引幂等靠"先删后插"**，否则改版后新旧内容并存；
3. **RRF 而不是加权求和**，否则两路量纲不同、一路压死另一路；
4. **限流拒绝不能计入熔断失败**，否则一次突发就把服务"打成 503"；
5. **向量按 `index` 归位**，否则向量与文本错位、检索结果莫名不准；
6. **RAGAS 要给 `RunConfig` 且关掉重试**，否则最慢的 faithfulness 永远 NaN。

这六条都能在 [项目7-设计与实施文档.md](项目7-设计与实施文档.md) 第 8 节"踩坑对照表"里找到现象与处置。
