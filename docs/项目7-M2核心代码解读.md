# M2 核心代码解读：search-service（检索链路）

> 配套：[项目7-设计与实施文档.md](项目7-设计与实施文档.md)（需求/架构/进度）
> 本文只讲 **M2 已实现的代码**：消费事件建索引 → 两路召回 → RRF 融合。
> 代码位置：`search-service/src/main/java/com/zjjxy/searchservice/`

---

## 0. 一条链路先看全

```
doc-service ──Kafka(doc-indexed)──> DocumentIndexedConsumer
                                        │
                                        ▼
                                  ChunkIndexService
                                  ├─ 删旧块（幂等）
                                  ├─ EmbeddingClient（bge-m3，1024 维）
                                  └─ insert doc_chunk（正文 + 向量 JSON）

用户 ──POST /search/hybrid──> SearchController
                                  │
                                  ▼
                            HybridSearchService
                            ├─ 关键词：DocChunkMapper.keywordSearch（ngram 全文索引）
                            ├─ 向量：EmbeddingClient.embedOne + cosine
                            └─ RRF 融合 → List<SearchHit>
```

两条线共用同一个 `EmbeddingClient`，但方向相反：建索引时是"批量 embed 文档块"，检索时是"单条 embed 查询"。

## 1. 事件契约：一个必须一字不差的对象

`event/DocumentIndexedEvent.java`：

```java
public record DocumentIndexedEvent(
        String eventId, Long docId, Long tenantId, String title,
        int version, List<Chunk> chunks, String occurredAt) {
    public record Chunk(int index, String content, int charCount) { }
}
```

它和 `doc-service` 里的同名类是**两份代码、同一份契约**。跨服务不共享类（不该为了一个 DTO 引入公共模块），代价是字段名必须手工对齐。

字段对不上的后果很隐蔽：JSON 反序列化时**缺失的字段直接是 null，不报错**。所以 `docId` 写成 `doc_id` 也能跑，只是每条事件入库时 `document_id` 都是 null。

要让反序列化用本地这个类，`application.yml` 里三行缺一不可：

```yaml
spring.kafka.consumer.value-deserializer: ...JsonDeserializer
properties:
  spring.json.trusted.packages: "*"
  spring.json.use.type.headers: false        # 忽略生产端写的类名
  spring.json.value.default.type: com.zjjxy.searchservice.event.DocumentIndexedEvent
```

> 生产端的 `JsonSerializer` 会把"它自己的类全限定名"塞进消息头。不关掉类型头，消费端就会拿着 `com.zjjxy.doc_service.event.DocumentIndexedEvent` 去找类，直接 `ClassNotFoundException`。

## 2. EmbeddingClient：批量 + 按 index 归位

### 2.1 分批

```java
for (int i = 0; i < texts.size(); i += BATCH_SIZE) {
    List<String> batch = texts.subList(i, Math.min(texts.size(), i + BATCH_SIZE));
    result.addAll(embedBatch(batch));
}
```

一篇文档切出 20 块，不能一次全塞过去（请求体太大、容易超时）。`BATCH_SIZE = 16` 是个经验值。

### 2.2 归位（这段最容易写错）

```java
float[][] ordered = new float[batch.size()][];
for (JsonNode item : resp.path("data")) {
    int idx = item.path("index").asInt(-1);
    if (idx < 0 || idx >= ordered.length) continue;
    ordered[idx] = toArray(item.path("embedding"));
}
```

服务端**不保证**返回顺序与入参一致。直接把 `data` 数组按顺序 add，向量就可能和文本错位一格。

错位的后果不是报错，而是"检索结果莫名其妙地不准"——A 文章的内容带着 B 文章的语义。这类 bug 靠肉眼几乎发现不了。

### 2.3 失败就抛，别在这里降级

```java
if (v == null) throw new IllegalStateException("embedding 返回条数不足，期望 " + batch.size() + " 条");
```

`EmbeddingClient` 只负责"要么拿到完整结果、要么抛异常"。**降级策略由调用方决定**：

- 建索引时失败 → 只存关键词（`ChunkIndexService` 决定）；
- 检索时失败 → 退化成仅关键词（`HybridSearchService` 决定）。

同一个客户端，两种降级语义，所以不能把 catch 写在客户端里。

## 3. ChunkIndexService：先删后插 = 幂等

```java
// 1) 幂等：清掉这篇文档的旧块（含旧版本）
int deleted = chunkMapper.delete(new QueryWrapper<DocChunk>()
        .eq("document_id", event.docId())
        .eq("tenant_id", event.tenantId()));

// 2) 批量算向量；失败降级为 null（只存关键词）
List<float[]> vectors = tryEmbed(contents, event.docId());

// 3) 逐条落库
row.setEmbedding(vectors != null ? toJson(vectors.get(i)) : null);
```

三个设计点：

| 设计 | 为什么 |
|---|---|
| **删除重建** | 文档改版会重发事件。不删就会出现新旧两份内容同时可检索，用户可能拿到已作废的条款 —— 比"搜不到"危险得多 |
| **`@Transactional`** | 删除和插入必须同生共死；否则删了旧的、插入失败，这篇文档直接从索引里消失 |
| **向量失败降级** | embedding 服务抖动时，宁可"这篇只有关键词索引"，也不要整篇建不进去。日志会记 `向量=无(降级)`，模型恢复后重发事件即可补齐 |

`toJson` 把 `float[]` 序列化成 JSON 数组存进 `LONGTEXT`。1024 维大概 1.2 万字符——这个量级还能接受，再大就该换向量库了。

## 4. Consumer：异常只记日志，不往外抛

```java
@KafkaListener(topics = "doc-indexed", groupId = "search-index-group")
public void onMessage(DocumentIndexedEvent event) {
    log.info("收到索引事件 docId={} version={} chunks={}", ...);
    try {
        indexService.index(event);
    } catch (Exception e) {
        log.error("建索引失败 docId={} version={}", event.docId(), event.version(), e);
    }
}
```

抛出去会触发 Kafka 默认重试；重试耗尽后要么跳过（丢消息），要么堵住分区（后面的文档全卡住）。

课堂版选择"记日志、继续消费"，保证一条毒消息不会拖死整条链路。生产上更稳的是失败进**死信队列（DLQ）**，再定时/人工重放。

`groupId` 决定分区分配：同一组内的多实例**分摊**分区，不会重复建索引；想重放历史消息就换一个 groupId。

## 5. DocChunkMapper：中文全文检索的关键是 ngram

```sql
SELECT id, document_id, tenant_id, chunk_index, content,
       MATCH(content) AGAINST (#{q} IN NATURAL LANGUAGE MODE) AS score
FROM doc_chunk
WHERE tenant_id = #{tenantId}
  AND MATCH(content) AGAINST (#{q} IN NATURAL LANGUAGE MODE)
ORDER BY score DESC
LIMIT #{limit}
```

两个细节：

1. **`MATCH` 出现两次不是笔误**：`WHERE` 里不能引用 `SELECT` 的别名，过滤条件必须再写一遍；否则会退化成"全表扫描 + 排序"，结果里全是 0 分。
2. **索引必须带 `WITH PARSER ngram`**（见 `deploy/init.sql`）。MySQL 默认分词器按空格切，中文整句会被当成一个词 —— 建了全文索引也永远查不到。`ngram` 按 2 字滑窗切，才能命中"年假""报销"这类词。

向量候选查询是另一条：

```sql
SELECT ... FROM doc_chunk WHERE tenant_id = #{tenantId} AND embedding IS NOT NULL
ORDER BY id LIMIT #{limit}
```

为什么不在 SQL 里算余弦：MySQL 没有向量类型和向量索引，SQL 里逐行解析 JSON 反而更慢。数据量小的时候"捞进内存算"最直接；量大就该上 pgvector / Milvus 了。`limit`（默认 2000）是保护，别把整库读进内存。

## 6. HybridSearchService：两路 + RRF

### 6.1 编排

```java
List<KeywordHit> keywordHits = chunkMapper.keywordSearch(query, tenantId, keywordTopK);
List<Scored> vectorHits = vectorSearch(query, tenantId);
return fuse(keywordHits, vectorHits, limit);
```

两路是**独立召回**的：关键词取前 10、向量取前 10，然后融合。不是"先关键词再向量补"，那样会把关键词的偏差一路带下去。

### 6.2 向量路：失败要降级

```java
try {
    queryVec = embeddingClient.embedOne(query);
} catch (Exception e) {
    log.error("query 向量计算失败，本次仅关键词检索：{}", e.getMessage());
    return List.of();
}
```

向量服务挂了返回空列表 → `fuse` 只拿到关键词的排名 → 检索退化成"纯关键词"，但接口仍然是 200。**检索降级，不是检索崩溃**。

### 6.3 余弦

```java
dot / (Math.sqrt(na) * Math.sqrt(nb))     // 任一范数为 0 返回 0
```

1024 维、几百个块，Java 里直接循环足够快（实测向量路 100~200ms，主要耗时是算 query 向量的网络调用）。

### 6.4 RRF 融合

```java
if (m.keywordRank != null) score += 1.0 / (rrfK + m.keywordRank);
if (m.vectorRank  != null) score += 1.0 / (rrfK + m.vectorRank);
```

`rrfK = 60`。rank=1 单路得 `1/61 ≈ 0.0164`，两路都是 rank1 得 `0.0328`。

**为什么不用加权求和**：关键词分是 MySQL 相关度（可能几十），余弦是 0~1。直接相加，关键词那一项会把向量分完全淹没——融合就名存实亡。RRF 只看名次，天然免疫量纲问题。

`Merge` 这个内部类用 `LinkedHashMap<Long, Merge>` 按 `chunkId` 归并，一路有、另一路没有的块也能进最终结果（只加一路的分）。

## 7. SearchController：为什么用 POST

```java
@PostMapping("/hybrid")
public List<SearchHit> hybrid(@RequestBody SearchRequest request) { ... }
```

用户的问题可能是一整段话（几十上百字），塞进 URL 会撞长度上限，也不方便日志脱敏。检索是"查询"但语义上是一次计算，用 POST + JSON body 更合适。

校验只有两条：`query` 非空、`tenantId` 非空。抛 `IllegalArgumentException`，由 `ApiExceptionHandler` 转成 400。

## 9. 踩坑清单（M2 相关）

| 现象 | 根因 | 处理 |
|---|---|---|
| 全文检索永远 0 条 | 索引用了默认分词器 | `FULLTEXT ... WITH PARSER ngram` |
| 消费端 `ClassNotFoundException` | 生产端在消息头写了它自己的类名 | `spring.json.use.type.headers: false` + `value.default.type` |
| 检索结果"莫名不准" | 向量没按 `index` 归位 | 用 `float[batch.size()]` 按下标填 |
| 文档改版后搜到旧内容 | 建索引没删旧块 | 先 `delete` 再 `insert` |
| yml 里 `default.type` 不生效 | 缩进多了一个空格，被解析成嵌套 | `spring.json.value.default.type` 与同级键对齐 |
| 接口整体 500 | embedding 失败被直接抛出 | 建索引/检索各自降级 |
