## 1. 镜像：三个 Dockerfile 覆盖五类产物

| 文件 | 用途 | 基础镜像 |
|---|---|---|
| `Dockerfile.java` | 4 个 Java 服务（`ARG JAR_FILE` 复用同一份） | `eclipse-temurin:17-jre-jammy` |
| `Dockerfile.metric` | Python 评测服务 | `python:3.11-slim` |
| `Dockerfile.web` | 前台 + 后台（nginx 静态托管 + 反代） | `nginx:1.27-alpine` |

### 1.1 为什么 Java 镜像不做多阶段构建

常见写法是 `FROM maven ... RUN mvn package` 再拷到 JRE 里。这里没这么做：

- jar 在 CI/本地已经由 Maven 打好，镜像里再 build 一次等于**构建两次、下载两次依赖**；
- 镜像的职责只有"运行"，多阶段构建会让 Dockerfile 承担 CI 的职责；
- 排查也简单：`docker build --build-arg JAR_FILE=...` 一眼就知道打的是哪个 jar。

### 1.2 三个必须加的运行时设置

```dockerfile
ENV TZ=Asia/Shanghai \
    JAVA_OPTS="-XX:MaxRAMPercentage=75 -Dfile.encoding=UTF-8"

RUN apt-get ... curl tzdata
HEALTHCHECK ... CMD curl -fsS http://127.0.0.1:${SERVER_PORT:-8080}/actuator/health
```

| 设置 | 不加会怎样 |
|---|---|
| `TZ=Asia/Shanghai` | 容器默认 UTC，日志时间比本地早 8 小时，跨服务对时间会疯 |
| `MaxRAMPercentage=75` | 容器里 JVM 默认按宿主机内存算堆，容易被 K8s OOMKill |
| `HEALTHCHECK` | 容器"活着"但接口没起来，编排层看不出来 |

### 1.3 `.dockerignore` 的一个坑

```gitignore
**/target/classes/          # 排除中间产物
**/target/generated-sources/
# 但不能排除 target/*.jar —— 它是构建输入！
```

最初写成 `**/target/`，结果 `COPY ${JAR_FILE}` 直接失败。**构建上下文里要保留 jar，只排掉 class/report 这些中间产物。**

### 1.4 镜像清单（实测构建成功）

```

skqa/doc-service:1.0.0     551MB
skqa/search-service:1.0.0  484MB
```

## 2. K8s 清单

```
deploy/k8s/
├── 00-namespace.yaml      skqa
├── 01-config.yaml         ConfigMap（Nacos/MySQL/Redis/Kafka 地址、TZ）
├── 02-secret.yaml         Secret（LLM/Embedding key，stringData 便于本地演示）
├── 10-gateway.yaml        Deployment(2) + Service
├── 11-doc-service.yaml    Deployment(2) + Service
├── 12-search-service.yaml Deployment(2) + Service
├── 13-ai-service.yaml     Deployment(2) + Service
├── 14-metric-service.yaml Deployment(1) + Service + emptyDir 挂样本
├── 15-web.yaml            Deployment(2) + Service
├── 20-ingress.yaml        nginx ingress → web
├── 30-hpa.yaml            只给 ai-service 配 HPA
└── nginx.k8s.conf         镜像内 nginx 配置（反代到 Service DNS）
```

### 2.1 几个刻意的取舍

| 决定 | 理由 |
|---|---|
| **metric-service 单副本** | 评测是旁路批处理，多副本反而要处理"样本放哪"的共享问题；它挂了不影响问答 |
| **只给 ai-service 配 HPA** | 它最贵（调大模型）也最容易被打满；给 gateway 扩副本没意义，瓶颈在 LLM |
| **探针用 `/actuator/health`** | 四个服务都引了 actuator，不用额外写健康接口 |
| **配置走环境变量** | `SPRING_DATASOURCE_URL`、`SPRING_DATA_REDIS_HOST` 都是 Spring Boot 的标准覆盖点，镜像不用改 |
| **Secret 用 `stringData`** | 本地演示方便；真实仓库应改用 SealedSecret / External Secrets / Vault |
| **中间件用 Service DNS** | `nacos:8848`、`mysql:3306`……真实生产换成云上托管实例的地址即可 |

### 2.2 web 镜像的 nginx 配置有两个版本

| 环境 | 配置文件 | 上游地址 |
|---|---|---|
| docker-compose（本机） | `web/nginx.conf` | `host.docker.internal:8080` |
| K8s | `deploy/k8s/nginx.k8s.conf` | `gateway:8080`（Service DNS） |

**这两个不能混用**：容器里没有 `host.docker.internal`，K8s 里也没有 `gateway` 这个宿主机名。

### 2.3 nginx 的启动期解析问题（实测踩到）

```
nginx: [emerg] host not found in upstream "gateway" in /etc/nginx/conf.d/default.conf:10
```

nginx **在启动时**解析上游域名，解析不到就直接退出。所以：

- 在 K8s 里：`gateway` Service 存在，没问题；但 web 若先于 gateway 起来会 crash-loop，靠 `restartPolicy: Always` 自愈；
- 单独 `docker run` 这个镜像必然失败（没有 `gateway` 这个名字）——冒烟测试要加 `--add-host`：

```bash
docker run -d -p 8899:80 \
  --add-host gateway:192.168.88.1 \
  --add-host metric-service:192.168.88.1 \
  skqa/web:1.0.0
```

实测结果：

```
GET /                        → 200  <title>企业知识库助手</title>
GET /api/doc/13?tenantId=1001 → 200
GET /api/actuator/health      → {"status":"UP"}
```

## 3. CI

`.github/workflows/ci.yml`，三个 job：

| job | 内容 | 为什么这么切 |
|---|---|---|
| `build-java` | `mvn verify`（JDK 17 + Maven 缓存） | 单元测试和编译问题早暴露，后面的 job 才有意义 |
| `build-python` | 装依赖 + `compileall` | 不做 RAGAS 实跑（要真实 key、要几分钟），只保证语法与依赖可解析 |
| `docker-images` | 打 5 个镜像 + `kubectl apply --dry-run=client` | 验证 Dockerfile 与清单在干净环境里也能跑通 |

CI 里的两个细节：

```yaml
env:
  LLM_API_KEY: "ci-placeholder"     # 测试不需要真实 key，更不能把 key 写进 CI
```

```yaml
run: ./kubectl apply --dry-run=client -f deploy/k8s/ --validate=false
```

`--dry-run=client` 不需要集群，但它仍会尝试连 API 做 discovery；CI 里用 `--validate=false` 绕开。

## 5. 从零部署到 K8s 的完整步骤（供真实环境参考）

```bash
# 1. 建命名空间与配置
kubectl apply -f deploy/k8s/00-namespace.yaml
kubectl apply -f deploy/k8s/01-config.yaml
# 2. 注入真实密钥（不要用仓库里的示例值）
kubectl -n skqa create secret generic skqa-secret \
  --from-literal=LLM_API_KEY=sk-xxx \
  --from-literal=EMBEDDING_API_KEY=sk-xxx
# 3. 建库表（MySQL 需先就绪）
mysql -h <mysql> -uroot -p < deploy/init.sql
# 4. 应用服务
kubectl apply -f deploy/k8s/10-gateway.yaml -f deploy/k8s/11-doc-service.yaml \
               -f deploy/k8s/12-search-service.yaml -f deploy/k8s/13-ai-service.yaml \
               -f deploy/k8s/14-metric-service.yaml -f deploy/k8s/15-web.yaml
# 5. 入口与弹性
kubectl apply -f deploy/k8s/20-ingress.yaml -f deploy/k8s/30-hpa.yaml
# 6. 验证
kubectl -n skqa get pods
kubectl -n skqa rollout status deploy/ai-service
```

## 6. 已知限制（诚实清单）

| 限制 | 影响 | 生产怎么做 |
|---|---|---|
| 无真实 K8s 集群 | 清单只做了结构与语法校验 | 装 kind/minikube 或上云 |
| Secret 明文示例 | 不能直接用于生产 | SealedSecret / External Secrets / Vault |
| 中间件假设外部就绪 | 清单里没有 MySQL/Kafka/Nacos 的 StatefulSet | 用云托管或 Helm chart 单独装 |
| 镜像无 registry 推送 | CI 只 build 不 push | 加 `docker push` + `imagePullSecrets` |
| Python 镜像未跑真实评测 | 只验证了构建 | CI 里用 mock 或录制样本做回归 |
