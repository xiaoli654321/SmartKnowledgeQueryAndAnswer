## 1. 项目定位与需求

### 1.1 一句话定位

企业内部智能知识问答平台：员工用大白话提问，系统从企业自己的文档里检索依据，再让大模型**基于检索结果**组织答案，并且**答案有出处、可溯源**。

### 1.2 为什么不是"直接问 ChatGPT"

直接问大模型，它可能一本正经地瞎编（幻觉）；RAG（Retrieval-Augmented Generation，检索增强生成）先把企业文档检出来，再让模型"照着材料回答"，所以能给出处、能核对。

### 1.3 三个核心用户场景

| 场景 | 链路 | 落在哪个服务 |
|---|---|---|
| 管理员上传文档 | 解析 → 切片 → 入库 → 发事件 → 建索引 | doc-service + search-service |
| 员工用大白话提问 | 混合检索 → 拼上下文 → 大模型答 → 带出处 | ai-service（依赖 search-service） |
| 系统被治理与评测 | Failover、限流熔断、Token 计量、RAGAS 评测 | ai-service 治理层 + metric-service |

### 1.4 需求拆解：九项能力与落地位置

| # | 能力 | 落地位置 | 状态 |
|---|---|---|---|
| 1 | 服务拆分 | gateway / ai / doc / search / metric | ✅ 5 个服务全部就位 |
| 2 | 事件驱动 | doc-service 发 `doc-indexed` → search-service 消费 | ✅ 双向打通（M1 生产 + M2 消费） |
| 3 | 多供应商 Failover | ai-service `List<LlmProvider>` 逐个降级 | ✅ M3（401 时自动切本地） |
| 4 | 限流 + 熔断 + 重试 | resilience4j 三件套 | ✅ M3（25 并发实测 21×200 + 4×429） |
| 5 | Token 计量 | Redis `token:tenant:{id}` / `token:provider:{name}` | ✅ M3 |
| 6 | 版本管理 | `kb_document_version` 追加式版本链 | ✅ M1 |
| 7 | RBAC | `@RequirePermission` + `X-User-Role` | ✅ M1（方法级），网关级待 M5 |
| 8 | Text2SQL | 自然语言 → 只读 SQL + 代码层硬校验 | 待后续 |
| 9 | RAGAS 评测 | Python metric-service，不入 Nacos、HTTP 直连 | ✅ M4 |

### 2.3 核心数据流

**写入链路（上传文档）**

```
管理员 → gateway(8080) → doc-service(8082)
              │
              ├─ 解析：txt/md/pdf/docx → 纯文本
              ├─ 切片：500 字/块，重叠 100 字
              ├─ 入库：kb_document + kb_document_version(version=1)
              └─ 事务提交后 → Kafka topic `doc-indexed`（带 chunks）
                                    │
                                    ▼
                            search-service(8083) 消费 → 写 doc_chunk（含向量）
```

**问答链路（M3 实现）**

```
员工提问 → gateway → ai-service(8081)
                        ├─ Feign → search-service：混合检索 topK
                        ├─ 组装 Prompt（问题 + 检索到的片段 + 要求给出处）
                        ├─ Failover + 限流 + 熔断 + 重试 → LLM
                        ├─ Token 计量 → Redis
                        └─ @Async → metric-service：异步送评测样本（不阻塞热路径）
```

## 3. 数据库设计

### 3.1 `doc_db`（文档服务）

```sql
CREATE TABLE kb_document (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id   BIGINT NOT NULL,
  title       VARCHAR(255) NOT NULL,
  content     LONGTEXT,                       -- 当前版本全文
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_tenant (tenant_id)
);

CREATE TABLE kb_document_version (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  document_id BIGINT NOT NULL,
  version     INT NOT NULL,
  content     LONGTEXT,
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_doc_version (document_id, version)
);
```

**设计要点**

- **版本表是追加式的**：只 INSERT，永不 UPDATE/DELETE 历史行。回滚 = 把老内容写回主表 + **追加一条新版本**，所以"任何时刻当时是什么内容"永远查得到。
- **`title` 只在主表**：版本表存正文就够，避免冗余导致两处不一致。
- **`content` 用 LONGTEXT**：TEXT 上限 64KB，一篇制度文档就会踩到 `Data too long`。

### 3.2 `search_db`（检索服务，M2 使用）

```sql
CREATE TABLE doc_chunk (
  id              BIGINT PRIMARY KEY AUTO_INCREMENT,
  document_id     BIGINT NOT NULL,
  tenant_id       BIGINT NOT NULL,
  chunk_index     INT DEFAULT 0,
  content         LONGTEXT,
  embedding       LONGTEXT,                    -- 1024 维 float 的 JSON 数组（bge-m3）
  embedding_model VARCHAR(64) DEFAULT 'BAAI/bge-m3',
  create_time     DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_doc (document_id),
  KEY idx_tenant (tenant_id),
  FULLTEXT KEY ft_content (content) WITH PARSER ngram   -- 中文关键词检索靠 ngram 分词器
);
```

> 讲义原话是"向量字段简化，生产用向量库"。这里用 JSON 文本存向量，量级小时足够；生产应换成 pgvector / Milvus。

## 5. 事件契约

**Topic**：`doc-indexed`（key = `docId`，保证同一文档进同一分区、顺序不乱）

```json
{
  "eventId": "e8de4216-a895-4f6e-beec-b69841128218",
  "docId": 8,
  "tenantId": 1001,
  "title": "年假政策",
  "version": 1,
  "chunks": [
    {"index": 0, "content": "XX科技有限公司 员工年假管理制度……", "charCount": 497},
    {"index": 1, "content": "用完毕，因公司原因导致未能休完的……", "charCount": 277}
  ],
  "occurredAt": "2026-11-19T23:01:31.562Z"
}
```

**为什么事件里直接带 chunks**：search-service 拿到消息即可建索引，不必回查 `doc_db`。否则检索服务会反向依赖文档服务，形成分布式里典型的坏耦合。

**为什么在事务提交后发**：先发消息再提交事务，一旦回滚，索引已经建好而库里没有文档，长期不一致。实现上用 `TransactionSynchronizationManager.registerSynchronization(...)` 的 `afterCommit` 回调。

### M2 检索链路（search-service）✅

| 能力 | 实现 |
|---|---|
| 事件消费 | `@KafkaListener(topics="doc-indexed", groupId="search-index-group")`；消费端关掉类型头、指定本地 DTO 反序列化 |
| 幂等建索引 | 先按 `(document_id, tenant_id)` 删旧块，再整批插入 —— 文档改版不会新旧内容并存 |
| 向量 | bge-m3（1024 维）；严格按响应里的 `index` 归位（服务端不保证顺序）；失败降级为"仅关键词索引" |
| 关键词路 | MySQL `MATCH(content) AGAINST (... IN NATURAL LANGUAGE MODE)` + `WITH PARSER ngram` 全文索引 |
| 向量路 | 捞该租户候选（上限 2000）进内存算余弦，取 topN |
| 融合 | RRF：`Σ 1/(60 + rank)`；返回 `keywordRank` / `vectorRank`，一眼看出是哪一路召回 |

| 用例 | 期望 | 实际 |
|---|---|---|

| 向量落库 | 1024 维 JSON | ✅ 每块约 12.7 KB |

## 8. 踩坑对照表

| 现象 | 根因 | 处理 |
|---|---|---|
| Maven 报 `version is missing`、读不了工程 | BOM 写在 `<dependencies>` 里，`import` scope 无效 | BOM 放 `<dependencyManagement>` |
| Nacos 客户端一直刷 `Client not connected` | 只映射了 8848，缺 grpc 9848/9849 | compose 补 `9848:9848`、`9849:9849` |
| 宿主 Java 连不上 Kafka | `advertised.listeners` 写成了容器内地址 | 改成 `127.0.0.1:9092` |
| 改了 yml 不生效，服务名还是旧的 | `target/classes` 残留旧 `application.properties`，且 properties 优先级高于 yml | `mvn clean` / IDEA Rebuild |
| 接口 404（走网关） | 网关加了 `StripPrefix=1` 但服务 controller 带 `/doc` 前缀 | 二者统一：本工程不加 StripPrefix |
| Feign 报 `No load balancer available` | 缺 `spring-cloud-starter-loadbalancer` | 补依赖 |
| 上传报 `MaxUploadSizeExceededException` | 默认单文件上限 1MB | `spring.servlet.multipart.max-file-size: 30MB` |
| insert 报 `Unknown column 'xxx'` | 实体字段比表列多 | 实体与 DDL 一一对应 |
| 空表算版本号 NPE | `MAX(version)` 返回 NULL | `IFNULL(MAX(version),0)` |
| 源码报 `非法字符: '\ufeff'` | 文件带 UTF-8 BOM | 存成无 BOM UTF-8 |
| 事件发了又回滚 | 在事务内直接发消息 | `afterCommit` 回调再发 |
| 中文全文检索永远 0 条 | 全文索引用了默认分词器 | 建索引时 `WITH PARSER ngram` |
| 消费端 `ClassNotFoundException` | 生产端在消息头写了它自己的类名 | `spring.json.use.type.headers: false` + `value.default.type` 指定本地类 |
| `curl -d` 传中文报 JSON parse error | PowerShell 把中文转成 ANSI | 写 UTF-8 文件后 `--data-binary @file` |
| 每次都走本地小模型、又慢又差 | Failover 排序比较器写反（`Boolean.compare(bContains, aContains)`） | 改成按 `contains("ollama")` 升序，云端在前 |
| 突发流量下用户看到 503 | 熔断器把"被限流"也当成供应商失败 | CB 配置 `ignore-exceptions: RequestNotPermitted` |
| 429 变成 500/503 | fallback 里抛的异常被外层再包一层 | fallback 只做状态码映射，已在 `retryExhausted` 里原样透传 `ResponseStatusException` |
| RAGAS 报 `context_relevancy` 不可导入 | 装的是 ragas 0.4，该指标已移除 | 无参考答案时只算 faithfulness / answer_relevancy |
| RAGAS 某指标返回 NaN | faithfulness 最慢，默认 180s 超时 + 重试叠加把它挤爆 | `RunConfig(timeout=300)` 且 `max_retries=0` |
| `-javaagent` 报 `Error opening zip file ... Smart` | 路径含空格，参数被截断 | 把 agent 复制到无空格路径（如 `D:\sw-agent`） |
| Grafana 面板全空 | `/actuator/**` 被网关 RBAC 拦成 403 | 网关放行 actuator 路径 |
| 4 个服务同时启动，有的注册失败 | Nacos 在并发注册下 `Client not connected` | 逐个启动，或等 Nacos 完全就绪 |
